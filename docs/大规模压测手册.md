# 大规模压测运行手册

> 在固定机器上跑统一台架，把日志返回给开发方，再据结果改内部实现。
> 公开接口、参数、事务/TTL 语义、磁盘格式是稳定约束；"签名没变"不代表行为没变，
> 所以测试同时检查正确性和资源成本。

test11 第二步 M124/M127 的扫描专项（包含内存表逻辑胜者延迟复制）：

```powershell
$env:LSM_SCAN_ROWS='20000000'; cargo test --offline --release --lib lsm_scan_row_cost -- --ignored --nocapture --test-threads=1
```

同库每臂重开，全量导出逐值核对；LSM_SCAN_ROWS 输出实际 point_probes/blocks。
该 fixture 为普通值，blob 与同 seq 歧义的回退由独立守卫验证，不能用普通值的零点探测替代回退成本。

已有该台架生成的 scale fixture 时，可设置 LSM_SCAN_EXISTING 为其目录并设置 LSM_SCAN_UPDATES。
后者指定已更新的前缀行数：键为 scale_key(i)，前缀值必须为 scale_val(i + LSM_SCAN_ROWS)，其余为 scale_val(i)。
入口检查 MANIFEST 存在，不会自动删除指定目录；它会执行每臂 1000 次回滚写，不能当作只读检查，也不能用于任意业务库。
每臂先抽样点读最多 200000 次，再做冲突检查探针，最后扫描全库逐值验收；输出 LSM_REUSE_GET / LSM_REUSE_CONFLICT / LSM_SCAN_ROWS。
不设置 LSM_SCAN_EXISTING 时仍自行 bulk 建库，LSM_SCAN_UPDATES 必须为 0；复用普通灌库后的库与 bulk 新库不是同一数据形状。
本轮原 20M 普通读写 ABBA 在首轮旧臂更新结束后中止，未取得完整通过；复用库的来源和验证证据见 M128。

M100 快照扫描及恢复对照：`cargo test --offline --release --lib memory_snapshot_scan_cost -- --ignored --nocapture --test-threads=1`。
`SNAPSHOT_ROWS` 默认 600000；旧/新/新/旧交替，每轮快照文件和恢复库均逐值验证。扫描旧臂保留逐键回查，
恢复旧臂保留逐行锁及原始键复制；M105 后新臂同时采用原始键移动，两臂均已使用编码键移动、当前缓冲/CRC/信封编码。
因此不能把这个持续演进的对照差值解释为 M99→M100 整包提速；单独核验 M105 请用上面的新入口。

M97 的定向复测命令：`cargo test --offline --release --lib scale_maintenance_recheck -- --ignored --nocapture --test-threads=1`。
默认 `RECHECK_ENGINE=memory`、`RECHECK_ROWS=10000000`、`RECHECK_ROUNDS=2`；另可指定 `bplus_tree` 或 `lsm_tree`。
可用 `SCALE_SCRATCH_DIR` 指定测试数据位置，正常结束由现有 RAII 回收本次目录。本轮先使用 D 盘
`target/test-data`，核验 D 为机械硬盘、原日志 C 为 SSD 后，后续验证转到 C 盘专用测试缓存目录；
必须记录实际介质，跨盘墙钟不能当代码 A/B。具体复测阶段与二进制哈希见 CHANGELOG。
它只覆盖灌库/重开/更新/health/vacuum/逐值验收，不代替五档完整台架；原台架也新增同一维护计量，
并在 bulk 重开后流式核验全部数据。SCALE_MAINT 的 LSM 数值为本引擎本轮累计值，阶段成本应做差；
自动回收状态属于当前实例，重开后会重置，不能跨重开相减。

M99 补 `RECHECK_UPDATE_STAGES`（begin/write/commit）与 `RECHECK_VACUUM_STAGES`；标准台架也输出
`SCALE_UPDATE_STAGES` / `SCALE_VACUUM_STAGES`。MaintenanceMs 每项是（调用次数，累计毫秒）。
B+ 的 checkpoint、WAL commit、自动回收与回收的 scan/delete/sync 均在实际入口计量；memory
记录自动回收及 scan/delete。auto_vacuum 内含三个回收子项，不能与子项相加。未插桩的入口输出零
不表示这些工作免费；探针只在测试构建显式 Scope 内生效。生产路径没有读钟成本。

M101 在 LSM 的真实回收入口补 scan/delete/sync、blob 引用扫描与文件回收计量；
`blob_point_reads` 是为收集引用额外读取存活编码键的次数。delete 或 sync 内可能触发 flush/compact，
不能再把 SCALE_MAINT 中这两项相加。没有 blob 文件的库应为 0；有 blob 时仍需完整收集引用。
同构建旧/新/新/旧对照用以下 PowerShell 命令（四轮均检查删除守恒并逐值核验）：

```powershell
$env:RECHECK_ENGINE='lsm_tree'; $env:RECHECK_ROWS='600000'; $env:RECHECK_ROUNDS='4'; $env:RECHECK_BLOB_COMPARE='1'; cargo test --offline --release --lib scale_maintenance_recheck -- --ignored --nocapture --test-threads=1
```

改跑普通新路径时设 `$env:RECHECK_BLOB_COMPARE='0'`。两臂只在全库 vacuum 的无 blob 文件跳过门不同；
同一进程串行运行，仍可能受到缓存/同步/系统负载影响，必须结合点读次数和分段计量判断。

## 四、判据与口径（怎么读结果）

### 通过判据

每档必须同时满足：

- 退出码 0
- 输出含 `SCALE_DONE rows=<规模> engines=4`
- 四家各打印 `SCALE_ENGINE_DONE`
- 132 个性能格全出（脚本自动数；M81 第 2 项把 `flush+merge` 拆成两格 122→126，第 4 项加
  `search 末页(免 total)` 一格 126→130，第 6 项把 memory 冷重开的两处特判拆成真格 130→132）
- 四家各打印 `migrate 验收通过(不计时) <规模+min(规模,1000)+1> 个唯一键`

**不以"进程退出 0"冒充通过。** 旧台架曾因拿源库自己的计数当期望、自洽地放过丢数据。

### 内存口径

| 字段 | 是什么 | 不是什么 |
|---|---|---|
| `常驻` MB | 该操作结束后仍活着的堆活字节增量 | 进程 RSS |
| `峰值 +` MB | 该操作期间的高水位增量 | 进程峰值 |
| `cache_budget_bytes` | 按样本槽价估算的缓存容量 | 进程 RSS 硬上限 |

MB 是 Rust 分配器记账的堆活字节 / 1e6，不是 Windows 任务管理器的进程内存。
**不能把 B+ 树冷重开那格的 0 MB 读成"运行总内存为 0"，也不能把各段峰值相加成 RSS。**

### 跨构建时间差只是线索

本机单样本墙钟跨轮漂 1.3~2.6 倍。**跨构建的时间差不能直接当算法进步**——
要拿同一次运行内的两臂比值、或同构建同档两趟取最小，才有因果意义。
性能结论只认计数（块访问、页访问、缓存未命中）。

## 六、台架测什么（132 格的来源）

每档四引擎各 33 格，共 132 格性能记录；额外诊断和计时外验收另列：

| 类别 | 操作 |
|---|---|
| 写入 | 灌入 / 更新 10% / 批量灌 / incr×1000 / set_with_ttl×1000 |
| 读取 | 点读 / multi_get / seek / seek_prev / get_ttl×1000 |
| 扫描 | scan / reverse_scan / prefix_scan / scan_page 翻完整库 / search 首页(免total) / search 末页(深翻) / search 末页(免 total) |
| 维护 | health() / vacuum() 全库 / vacuum_bounded 一片 / flush / merge / 冷重开 / 再冷重开 |
| 导出 | export 全库(物化) / export 流式(逐行落地) |
| 搬运 | migrate → memory / bulk 灌 |
| 启动 | open 空库 / flush+checkpoint |

每格报：单位耗时（µs/次 或 µs/行）、常驻增量 MB、峰值增量 MB、额外计数（如"裁掉 35424 行""磁盘 116.5 MB"）。

**验收政策（2026-10-31 改）：**
- TTL 两格仍量真实 `set_with_ttl` / `get_ttl`。
- 紧接着在计时外核值再 `persist_key` 取消期限，新增最多 1000 个辅助版本。
- 后续迁移期望固定 `rows + min(rows, 1000) + 1`，按**独立种子**逐键逐值验收，不拿源库 health 当正确性分母。
- 验收和准备不计入每引擎 33 格性能记录；新增辅助版本会在输出里单独交代，不冒充历史 TTL 同形状。
- `search 末页(免 total)`（M81 第 4 项；**11-04 起四家都走反向逐步退**）：`lsm_tree` 走 SST 块读，
  其余三家走 `back_n_with`（页宽把候选键反向退，bplus/memory 先右路下降取库尾）。这一格**不是**
  "如实付反向原语的缺"那种读数了 —— 旧构建（`test1`/`test2`/`test3` 三趟都算）里三家停在 trait
  默认的 `reverse_scan` 截尾 = O(库)（20M：`test2` 87.9 / 54.6 / 63.8 s、`test3` 105.6 / 71.4 / 68.9 s，
  常驻 +2147.5 MB、峰值 +4771 MB），跨这条线比秒数没有意义。有界性由计数守卫钉住：
  三家 `back_n_candidates ≈ 页宽` 且 `back_n_fallbacks == 0`（常态快路径）。
  M93 更新：强制回退仍可能走完整库，但只缓存一页结果；时间界与内存界分别验收。
  ⚠️ 别拿它与 `search 末页(深翻)` 折成 µs/行 对拍：那一格要精确 total（数全库是主导）且行数是
  正确的末页余量（整除页宽时为整页），这一格最多取页宽行、不数 total ⇒ 只能同列 µs/次 看。
  M98 修订：test5 及更早台架使用 rows / page_size，五档整除时实际请求越界空页；
  那些读数只能作为全库计数/越界查询耗时，不能作为正确末页取值证据。现已更正并在计时外逐值验收。

**跨版本比读数时必须知道这三条（M81 第 2 项改的形状 + M82 改判的一趟）：**
- `flush+merge`（122 格时代的一格）= 现在的 `flush` + `merge` **两格之和**；旧的 20M 档 113.5 s 里
  bitcask 几乎全是 merge（同格 bplus 只有 18.5 µs ⇒ flush 是零头），所以旧那一格要当"两格合并"读。
- `vacuum() 全库` 从 M81 起**不再自带 merge**（bitcask 的 20M 档 166.9 s 里含一次全库重写，约 113 s）⇒
  跨版本比这一格要先减掉那笔，或改看 `vacuum + merge` 两格之和。硬删除的空间现在等显式 `merge()`；
  长跑那一头由 `crate::maintenance::Maintenance` 的全库收尾带上（`vacuum()` + `merge()` 两步）。
- **`docs/test2.txt` 那趟（v0.5.0 含 `339a559`）的 `灌` / `更新 10%` / memory `冷重开`、以及冷重开后
  memory 的单事务格（`multi_get`/`seek_prev`/`get_ttl`/`incr`）都带着一笔自动回收的税**：那份实现让
  每次 `begin()` 在一轮开着时都扫一整片（16 Ki 行），写流里一轮永远开着 ⇒ 1000 行/事务放大 16×。
  同一趟的 `vacuum() 全库` 格因此只裁"残余"（20M bitcask/bplus 裁 4000 行，旧趟 1001576）——
  **工作量不等，不能直接比秒数**。M82 已拿掉那一支并用计数守卫钉住（详见 CHANGELOG M82 节）；
  600k 冒烟上这几格全部回到 42ca438 的水平（`灌` bitcask 47.2→28.2、memory `冷重开` 4.39→1.55 s、
  `seek_prev` 15 516→36.6 µs、vacuum 裁 36424 行）。
- **11-04 那趟（M82 尾巴）又挪了两格的台阶**，同样是"跨线不可比"：① 三家
  `search 末页(免 total)` 从 O(库) 变成 O(页)（600k 档 bitcask 2 283 567 → 432 µs、
  bplus 1 296 165 → 1162 µs、memory 858 578 → 231 µs；20M 档旧读 87.9~105.6 / 54.6~71.4 /
  63.8~68.9 s 不可再与它同列）
  ⇒ `test1`/`test2`/`test3` 三趟的那一格都是旧台阶；
  ② memory `冷重开`/`再冷重开` 去掉了"重放时逐页扫零垃圾"那笔账（600k：1.55→0.96 s / 1.56→1.02 s，
  test2 那趟 4.39/5.49 s）⇒ 这一格的旧读数偏高。四家 `末页(免 total)` 与 lsm `首页(免 total)` 之外
  的格不受这两刀影响（600k 冒烟里 `灌`/`更新`/`vacuum`/`health rows` 与上一构建同量级）。

### 20M 档 memory 启停快照的实测（M81 尾巴 C，2026-11-02，v0.5.0 构建）

| 格 | 读数 | 怎么读 |
|---|---|---|
| `flush+checkpoint` | 0.2 µs，**磁盘 0.0 MB** | 运行期一律不碰快照文件 —— 这条口径在大档上的直接实证 |
| `停止落盘`（不计时行） | **44 672.1 ms** | `Drop` 里写出 2000 万行整库快照的耗时 |
| 快照体积 | **2168.9 MB**（`flush` 那行的"磁盘"列） | 20M 档 `snapshot.bxp` ≈ 2.12 GB |
| `冷重开(恢复)` | **305.37 s**，常驻 3867.9 MB，峰值 +6037.0 MB | 读回那份快照 + 逐行重放进库里 |
| `再冷重开` | **332.14 s**，常驻 4256.0 MB，峰值 +6643.2 MB | 第二次启停（多 200 万行 bulk）⇒ 读回更贵 |
| 四家 `migrate → memory` 验收 | 各 20001001 唯一键全过，TTL=0 | 搬运保真与快照无关，同趟顺手核 |

第二趟（`docs/test2.txt`）同格读 **停 35.8 s / 起 208.6 s / 再起 242.8 s / 2168.9 MB**（本机单样本噪声 1.5×；

第三趟（`docs/test3.txt`，M82 构建，税已拿掉）同格读 **停 37.1 s / 起 50.7 s / 再起 76.5 s**
（常驻 3867.9 / 4256.0 MB）—— **这一行才是这一格的当前价**：起停的 4~5 倍差全在那笔税里。
⚠️ 11-04 构建又去掉了**重放期逐页扫零垃圾**那笔账（§四 第四条；600k 档 `冷重开` 1.55 → 0.96 s、
`再冷重开` 1.56 → 1.02 s）⇒ 表里这两格在 11-04 之后的构建上还会更低，拿旧表比要记得这两刀。
`is_production_ok() == false` 没有因此改变 —— 快照不是 WAL：崩溃（`std::process::exit` / 断电）不保存任何东西。
⚠️ 同趟另两格要分开读：memory 的 `search 末页(免 total)` **115.98 s** 是"三家的末页当时还没有反向
原语"那一格（对 memory 是 O(库) + 2147.5 MB）—— **11-04 构建已补上原语**（600k 档 115.98 s → 0.23 ms，

## 八、给开发方的反馈格式

测完后把以下信息发给开发方，按这个顺序：

1. **`summary.json` 全文**（一眼看 PASS/FAIL 和哪个引擎红）
2. **`run.json`**（确认是哪个代码版本、哪个二进制）
3. **失败的 `rows_*.log`**（含 `scratch=`、`SCALE_ENGINE_DONE`、panic 信息）
4. 如果某个性能格异常（比如某家 µs 比同档其它家高 10 倍），附对应的 `rows_*.csv` 那一行

开发方按结果改内部逻辑，不动接口/参数/语义/磁盘格式。如果哪次确实需要动这些合同，会先说明。
