# 大规模压测运行手册

> 在固定机器上跑统一台架，把日志返回给开发方，再据结果改内部实现。
> 公开接口、参数、事务/TTL 语义、磁盘格式是稳定约束；"签名没变"不代表行为没变，
> 所以测试同时检查正确性和资源成本。

---

## 一、准备（每次新机器只做一次）

```powershell
cd D:\develop\workspace\rust_workspace\storage-engines

# 确认有 Rust 工具链
cargo --version        # 需要 1.85+（edition 2024）
rustc --version

# 确认磁盘空间：2000万档约需 2 GB 测试数据空间 + 2 GB 临时日志
# 推荐把 scratch 放到有空间的盘（默认在仓库 data/bench-scratch）
```

机器要求：Windows 10+、PowerShell 5.1+、单进程单线程运行（内存计量是进程级的）。
内存参考：2000 万行内存档约需 4 GB 可用内存。

## 二、运行压测

### 方式一：脚本（推荐 —— 自动记指纹、出 summary/CSV、自动清理）

```powershell
cd D:\develop\workspace\rust_workspace\storage-engines

# 0) 脚本自检（不编译、不跑大档，几秒钟）
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\run-scale-bench.ps1 -SelfTest

# 1) 单跑 60 万（建议第一枪）
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\run-scale-bench.ps1 -Rows "600000"

# 2) 全套五档顺序跑：60万 → 100万 → 500万 → 1000万 → 2000万（默认就是这套）
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\run-scale-bench.ps1

# 3) 自选档位 + 重复次数 + 把测试数据放别的盘
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\run-scale-bench.ps1 -Rows "1000000,5000000,10000000,20000000" -Repeat 1 -ScratchRoot "D:\storage-bench-scratch"

# 4) 首次在新机器跑、离线构建报缺依赖时加 -AllowNetwork
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\run-scale-bench.ps1 -Rows "600000" -AllowNetwork

# 5) 强杀/断电后，按上次结果目录的清单清理测试库（不会碰别的）
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\run-scale-bench.ps1 -CleanRun "D:\develop\workspace\rust_workspace\storage-engines\data\bench-results\<上次那个时间-UUID目录>"
```

**脚本参数说明：**

| 参数 | 默认 | 说明 |
|---|---|---|
| `-Rows` | `600000,1000000,5000000,10000000,20000000` | 逗号分隔的行数列表 |
| `-Repeat` | `1` | 每档重复次数（两趟取最小，用于量噪声地板） |
| `-OutputRoot` | `data/bench-results` | 日志/摘要输出目录 |
| `-ScratchRoot` | `data/bench-scratch` | 测试库临时目录 |
| `-AllowNetwork` | 关 | 离线构建缺依赖时打开 |
| `-SelfTest` | — | 只测脚本本身，不编译不跑大档 |
| `-CleanRun <目录>` | — | 强杀后按清单清理该次残留 |

### 方式二：不用脚本，直接 cargo 跑固定档位（IDE 里也用这个）

```powershell
cd D:\develop\workspace\rust_workspace\storage-engines

# 60 万
cargo test --release --lib engine::tests::scale_bench::rows_600000 -- --exact --ignored --nocapture --test-threads=1

# 100 万
cargo test --release --lib engine::tests::scale_bench::rows_1000000 -- --exact --ignored --nocapture --test-threads=1

# 500 万
cargo test --release --lib engine::tests::scale_bench::rows_5000000 -- --exact --ignored --nocapture --test-threads=1

# 1000 万
cargo test --release --lib engine::tests::scale_bench::rows_10000000 -- --exact --ignored --nocapture --test-threads=1

# 2000 万
cargo test --release --lib engine::tests::scale_bench::rows_20000000 -- --exact --ignored --nocapture --test-threads=1

# 任意自定义规模（比如 200 万）走原入口
$env:SCALE_ROWS="2000000"; cargo test --release --lib engine::tests::scale_baseline_all_engines -- --exact --ignored --nocapture --test-threads=1
```

**三个必须：**

- 必须 `--release`（debug 构建慢几倍，数据无意义）
- 必须 `--exact --ignored`（否则不跑、或乱跑别的 ignored 测试）
- 必须 `--test-threads=1`（内存计量是进程级的，并行会互相污染）

不想要满屏输出就去掉 `--nocapture`。

cargo 方式默认把测试库写到 `%TEMP%`；想统一管理设：

```powershell
$env:SCALE_SCRATCH_DIR="D:\develop\workspace\rust_workspace\storage-engines\data\bench-scratch"
```

## 三、测完返回什么

### 脚本方式

把整个结果目录里的这三个文件给开发方（FAIL 再附对应 `rows_*.log`）：

```powershell
# 找最新结果目录
Get-ChildItem D:\develop\workspace\rust_workspace\storage-engines\data\bench-results | Sort-Object LastWriteTime -Descending | Select-Object -First 1

# 目录里要给的是：
#   summary.json    每档 PASS/FAIL、退出码、126格数量、cleanup 状态
#   run.json        Git HEAD、源码与二进制 SHA256、环境
#   rows_*_pass_*.csv  原始操作名、单位耗时、堆常驻/峰值增量、额外计数
#   (FAIL 时) 同名 .log 完整 stdout/stderr，含独立迁移验收和失败定位
```

### cargo 方式

把终端输出整段复制给开发方（含 `scratch=` 那行——强杀后清理要用它精确目录）。

## 四、判据与口径（怎么读结果）

### 通过判据

每档必须同时满足：

- 退出码 0
- 输出含 `SCALE_DONE rows=<规模> engines=4`
- 四家各打印 `SCALE_ENGINE_DONE`
- 126 个性能格全出（脚本自动数；M81 第 2 项把 `flush+merge` 拆成两格 ⇒ 122→126）
- 四家各打印 `migrate 验收通过(不计时) <规模+min(规模,1000)+1> 个唯一键`

**不以"进程退出 0"冒充通过。** 旧台架曾因拿源库自己的计数当期望、自洽地放过丢数据。

### 内存口径

| 字段 | 是什么 | 不是什么 |
|---|---|---|
| `常驻` MB | 该操作结束后仍活着的堆活字节增量 | 进程 RSS |
| `峰值 +` MB | 该操作期间的高水位增量 | 进程峰值 |
| `cache_budget_bytes` | 按样本槽价估算的缓存容量 | 进程 RSS 硬上限 |

MB 是 Rust 分配器记账的堆活字节 / 1e6，不是 Windows 任务管理器的进程内存。
**不能把 B+ 树冷重开那格的 0 MB 读成"运行总内存为 0"，也不能把各段峰值相加成 RSS。**

### 跨构建时间差只是线索

本机单样本墙钟跨轮漂 1.3~2.6 倍。**跨构建的时间差不能直接当算法进步**——
要拿同一次运行内的两臂比值、或同构建同档两趟取最小，才有因果意义。
性能结论只认计数（块访问、页访问、缓存未命中）。

## 五、清理范围

- 每档建唯一 scratch 目录并写 ownership marker，Rust RAII + 脚本 finally 两层清理。
- 断言失败也清理，只留结果日志/摘要。
- **不会清理**用户原库、其它运行目录、`backups/` 或共享 `target/` 编译缓存。
- 强杀整个脚本、断电不会执行 finally，此时用 `-CleanRun` 按清单清理。
- `-CleanRun` 只接受清单与 marker 匹配的目录，发现链接或归属不符会拒绝；不会按后缀/时间通配删库。

```powershell
# 看 scratch 目录（cargo 方式强杀后残留在这）
dir D:\develop\workspace\rust_workspace\storage-engines\data\bench-scratch -Recurse

# 手动删某个 cargo 跑出来的残留（先核对日志里的 scratch= 路径）
Remove-Item "D:\...\se_engine_xxx" -Recurse -Force
```

## 六、台架测什么（126 格的来源）

每档 × 四引擎 × 33 类操作：

| 类别 | 操作 |
|---|---|
| 写入 | 灌入 / 更新 10% / 批量灌 / incr×1000 / set_with_ttl×1000 |
| 读取 | 点读 / multi_get / seek / seek_prev / get_ttl×1000 |
| 扫描 | scan / reverse_scan / prefix_scan / scan_page 翻完整库 / search 首页(免total) / search 末页 |
| 维护 | health() / vacuum() 全库 / vacuum_bounded 一片 / flush / merge / 冷重开 / 再冷重开 |
| 导出 | export 全库(物化) / export 流式(逐行落地) |
| 搬运 | migrate → memory / bulk 灌 |
| 启动 | open 空库 / flush+checkpoint |

每格报：单位耗时（µs/次 或 µs/行）、常驻增量 MB、峰值增量 MB、额外计数（如"裁掉 35424 行""磁盘 116.5 MB"）。

**验收政策（2026-10-31 改）：**
- TTL 两格仍量真实 `set_with_ttl` / `get_ttl`。
- 紧接着在计时外核值再 `persist_key` 取消期限，新增最多 1000 个辅助版本。
- 后续迁移期望固定 `rows + min(rows, 1000) + 1`，按**独立种子**逐键逐值验收，不拿源库 health 当正确性分母。
- 验收和准备不计入 33 类性能格；新增辅助版本会在输出里单独交代，不冒充历史 TTL 同形状。

**跨版本比读数时必须知道这两条（M81 第 2 项改的形状）：**
- `flush+merge`（122 格时代的一格）= 现在的 `flush` + `merge` **两格之和**；旧的 20M 档 113.5 s 里
  bitcask 几乎全是 merge（同格 bplus 只有 18.5 µs ⇒ flush 是零头），所以旧那一格要当"两格合并"读。
- `vacuum() 全库` 从 M81 起**不再自带 merge**（bitcask 的 20M 档 166.9 s 里含一次全库重写，约 113 s）⇒
  跨版本比这一格要先减掉那笔，或改看 `vacuum + merge` 两格之和。硬删除的空间现在等显式 `merge()`；
  长跑那一头由 `crate::maintenance::Maintenance` 的全库收尾带上（`vacuum()` + `merge()` 两步）。

## 七、已知问题与待办

- **B+ 树迁移比其它家少 1 行**：600k 档实测 `601000` vs 其它家 `601001`，53 字节值（普通键）。
  旧断言拿 B+ 自己的 health 当期望，它自己也数 601000，自洽放过。新独立验收抓到了。
  **未修前每档都会在 B+ migrate 那格红。** 修完复绿后再跑大档。
- **LSM 大库查询单价随 SST 篇数线性涨**：1000 万行 `seek_prev` 319 块/次（100 万 35 块），缓存未命中恒 0。
  已量出候选剪枝的理论上限（~7~8 块），实现已合入并过 7 条剪枝守卫。
  **剪枝后五档实测已跑**（`docs/test.txt`）：`seek_prev` 600k→20M 单价 134.6→162.2 µs（行数 33×、单价 1.2×）⇒ O(块) 成立。
- ~~**20M 从未跑完**~~ **20M 已跑通**（`docs/test.txt` 五档全绿，20M 档 `test result: ok`，9294.8s）。
  此前的"~640 块/次"确是投前外推；正式产物建议下次走 `run-scale-bench.ps1` 落 summary.json/CSV。

## 八、给开发方的反馈格式

测完后把以下信息发给开发方，按这个顺序：

1. **`summary.json` 全文**（一眼看 PASS/FAIL 和哪个引擎红）
2. **`run.json`**（确认是哪个代码版本、哪个二进制）
3. **失败的 `rows_*.log`**（含 `scratch=`、`SCALE_ENGINE_DONE`、panic 信息）
4. 如果某个性能格异常（比如某家 µs 比同档其它家高 10 倍），附对应的 `rows_*.csv` 那一行

开发方按结果改内部逻辑，不动接口/参数/语义/磁盘格式。如果哪次确实需要动这些合同，会先说明。

```
storage-engines/
├── src/scale_bench.rs              固定五档测试入口（include 进 engine::tests）
├── src/engine.rs                   run_scale_baseline(rows) 台架本体
```

普通 `cargo test` 不跑这些大档（都是 `#[ignore]`）。
不带精确过滤直接跑所有 ignored 测试会乱跑别的，**不要这么干**。
