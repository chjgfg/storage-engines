## 第 1 项：LSM `search 首页(免 total)` 剪枝

### 问题

`search 首页(免 total)` 只取前 100 行，lsm 随库涨（`docs/test.txt`：600k=9.3ms → 5M=18.8ms → 10M=52.5ms；20M 回落到 40.9ms——单价跟**当档篇数**走，不随行数单调），bitcask/bplus 平（2~5ms）。

### 根因（已回读确认）

`lsm_tree.rs:4087` `LightMerge::new` 循环第 4091 行 `it.next()` **对每个源都调一次**，每个源读首块进堆。首页 `pattern=""` ⇒ `lo=None, hi=None` ⇒ `may_overlap_half_open` 对所有源成立 ⇒ 10M 档 597 个 SST 全初始化。

### L0 前提（已核实）

`for_mvcc()`（`lsm_tree.rs:154`）设 `l0_compact_threshold: 8`。bench 用 MVCC 模式 ⇒ L0 平时 ≤ 8 文件（`l0_compact_threshold: 8` 是**触发线**不是硬上限，slowdown 12 / stop 32 之下瞬时可更多）。L0 全初始化的账按十几个源兜，仍可忽略。惰性化只救 L1+。

### 机制（改正：不用堆哨兵）

**惰性源不进堆，用外部待激活列表。** L1+ 按 `min_key` 升序非重叠（`level_ranges_ordered` 为 true 时），惰性源按 `min_key` 排好存 `Vec`。堆里只有：memtable + imutables（内存，零成本）+ L0（≤ 8 个，全初始化）+ 已激活的 L1+ 源。

`next()` 每次 pop 后检查：堆顶 key 是否 **>=** 下一个未激活 L1+ 源的 `min_key`——是就**循环**激活（`while` 下一个源的 `min_key <= 堆顶键`；跨层可能有多个源共享同一个 min_key，单次 if 不够），激活 = 调 `light_iter(from,to,snap).next()` 真读一块，有结果 push 进堆；无论有没有结果都推进 `next_lazy`。

**为什么必须是 `>=` 不是 `>`**：初版写 `>`，在 `max_key[i]==min_key[i+1]` 相接端点上**永远不会触发**——堆顶键 == `min_key` 时 `>` 不成立，该源不激活，当前键就按已激活源的 seq 定论直接吐。若未激活源那行 seq 更新（或是个 Drop），吐出来的是旧值/不该吐的；等堆顶越过 `min_key` 再激活，它的首键又把同一把键在更大的键后面再吐一遍——乱序 + 重复。`>=` 让端点键在吐出前把未激活源折进 `pending` 的 seq 比较，与 eager 行为对齐；多花的只有端点相接那一瞬（文件边界上至多一次多余块读），剪枝收益不变。

**为什么不能用哨兵进堆**：`light_iter` 首个输出键不一定等于 `min_key`（`snap_seq` 截断前几条时首个可见键 > min_key）。用 `min_key` 当哨兵进堆会乱序。外部列表只拿 `min_key` 当"要不要激活"的判据，不参与堆排序，避开这个问题。

### 关键不变量

`LightMerge::next` 的 `pending`（`lsm_tree.rs:4123`）同键跨源比 seq 定胜者。激活判据改 `>=` 之后这条不变量**自动满足**：端点键被吐出前，持有它的未激活源必已进堆、必然走 `pending` 的 seq 比较分支——不需要额外特判，需要的是别把判据写回 `>`。

### 初始化边界（堆空时）

如果 memtable、L0 都空（bench 跑完 vacuum 后有可能），堆初始时没有即刻源，`next()` 的"pop 后检查激活"永远不会触发——堆是空的。**必须在 `new()` 或第一次 `next()` 前先激活第一个 L1+ 惰性源**：

```rust
fn new(...) -> Self {
    // ... 装 immediate 源（memtable/immutables/L0）进堆
    // 如果堆空且有待激活的惰性源，先激活第一个：
    if self.heap.is_empty() && !self.lazy_descriptors.is_empty() {
        self.activate_lazy(0);  // 调 light_iter().next()，push 进堆
    }
}
```

`activate_lazy(i)`：调 `lazy_descriptors[i].sst.light_iter(from, to, snap).next()`，有结果就 push `MergeNode` 进堆并记 `head`，同时 `next_lazy = i + 1`。

**迭代中途堆空**（初版没堵的第二处）：A 段 `[1..10]` 耗尽、B 段 `[20..30]` 尚未激活——pop 10 时判 `10 >= 20` 不成立（此刻不激活是对的），随后堆空、循环退出，**B 整段静默丢掉**。`next()` 里要兜同一条：堆空且还有惰性源 ⇒ 无条件激活下一个（它剩下的键必然大于一切已吐出的键，单调性不破），然后继续循环。推荐把 `new()` 里的 Bootstrap 和这一条合成一个口子：`next()` 循环顶上先查"堆空且还有惰性源 ⇒ 激活"，`new()` 里那段就可以删。

### 乱序回退

`!level_ranges_ordered[level]` 的层全初始化（和现在一样），与 `find_back` 回退同源。

### 结构落点（二审补）

- `LightMerge` 从"握迭代器"改成"握描述符"：`light_iter_range` 对 L1+ 不再建 `Box<dyn Iterator>`，改传 `(&SstFile, from, to, snap)` 描述符（mem / immutables / L0 照旧当场建迭代器进堆）。对外签名不变，调用方无感。
- **激活后的迭代器要留在槽位里**（`advance(src)` 之后还得继续拉）：槽位从"一个迭代器"变三态——未激活（描述符）/ 已激活（`Box<dyn Iterator>`）/ 已耗尽；`head` 按含惰性槽的全量源数预分配。
- 惰性列表是**跨层全局**按 `min_key` 排序——"非重叠"只在层内成立，跨层重叠是常态；堆 + `pending` 本来就吃跨层同键，激活判据不依赖非重叠。乱序层（`level_ranges_ordered[level] == false`）的文件照旧当场初始化。
- 惰性源的 `src` 用它在原源序里的**预分配下标**，激活时不重编号（`MergeNode` 同键平局按 src 定先后，"源序号小 = 更新"靠它）。
- 生命周期摩擦预警：激活发生在 `&mut self` 的 `next()` 里，`sst.light_iter(from, to, snap)` 又要借描述符里的 `&SstFile` 和界——先把这几个引用拷出来再 push 堆，别跟 `self.heap` 的可变借用撞车。

### 爆炸半径

`LightMerge` 被 `scan_page`/`export`/`vacuum_bounded`/`collect_rows`/`search_page_walk` 全用（后三者都汇到 `scan_candidates`，`lsm_tree_mvcc.rs:1161`），整库消费者有三处（初版漏了两处、二审又漏一处）：`scan_latest_light`（`lsm_tree.rs:1180`）、`count_kinds_at`（`lsm_tree.rs:1647`，**KV 层** health 的分 kind 计数）、**MVCC 层 `health()`**（`lsm_tree_mvcc.rs:531-542`，`rows/max_chain` 版本链统计，`None,None` 全库一趟——与 `count_kinds_at` 是两回事）。调用方全集已 grep 钉死，再无第四处。白送的对拍：health 有现成守卫 `test_health_does_not_materialize_its_sources`，且它注释要求看到的行集合与 `MVCC::vacuum` 严格一致——惰性化后这条天然就是"全库走查正确性"守卫。改错一处全错。必须跑 `txn_kernel_agrees_across_engines` + 全量 scan 逐行对拍。

## 第 3 项：bitcask merge 按段增量（两趟）

### 先量构成（必做前置）

`bitcask.rs:1483` merge 单趟：走 KeyDir（BTreeMap，内存）→ 每条 `read_live`（`bitcask.rs:1410`，seek+read，**不是 mmap**）→ append。20M 档 113s（`docs/test.txt` flush+merge 格 113.5s；bplus 同格 18.5µs ⇒ 这 113.5s 几乎全是 merge）。

`read_live` 走 `Log::read_value`（`bitcask.rs:1002-1011`：flush_buf → seek → read_exact，已核，**不是 mmap**）。OS page cache 可能命中（20M 档盘上 ≈ 3.6 GB——test.txt：灌完 flush 后 3608.9 MB；机器 64GB 装得下），也可能不。**加计时探针量三段**：

```rust
pub fn merge(&mut self) -> Result<()> {
    let t0 = Instant::now();
    // 走 KeyDir 只 collect (key, loc)，不 read_live
    let t_walk = t0.elapsed();
    let t1 = Instant::now();
    // read_live + append（当前逻辑）
    let t_rw = t1.elapsed();
    eprintln!("merge_profile walk={t_walk:?} read+append={t_rw:?}");
}
```

跑 100 万看比例。`read+append` > 60% 才值得改。

### 改法（两趟，不是单趟）

KeyDir 是按 key 排序的 BTreeMap，不按 file_id。要"只取指向某 file_id 的条目"得遍历全 KeyDir 过滤。所以：

**第一趟**：走 KeyDir，按 file_id 累加存活字节（墓碑不算，`KeyLoc::Live{file_id,_,len}` 才加；`SoftTombstone` 跳过）。内存 = `HashMap<u32,u64>`，小。

```rust
fn segment_live_bytes(&self) -> HashMap<u32, u64> {
    let mut live = HashMap::new();
    for loc in self.key_dir.values() {
        if let KeyLoc::Live { file_id, pos: _, len } = loc {
            *live.entry(*file_id).or_default() += *len as u64;
        }
    }
    live
}
```

**第二趟**：再走一遍 KeyDir，对指向脏段（存活率 < 阈值，默认 0.5）的 file_id 的条目：

- `KeyLoc::Live` ⇒ `read_live` + append 到该脏段的新段，就地改 KeyLoc；
- `KeyLoc::SoftTombstone` ⇒ **`write_soft_tombstone` 重写进新段**（现行 merge 在 `bitcask.rs:1545-1547` 就是这么做的）。墓碑行本身住在脏段里，跳过它 = 删旧段后 KeyDir 指向已删文件，重启走 hint / 全量重扫时这一支没人兜，最坏是键复活。重写墓碑不读值，便宜。

干净段的条目跳过（它们的 KeyDir 指针不动，磁盘段不动）。

比当前单趟多一次 KeyDir 走查（内存，快），但省了干净段的 read_live+append。

### KeyDir 更新策略（和当前 merge 完全不同）

当前 merge（`bitcask.rs:1631-1668`）是**全量重建**：删 hint → `key_dir = KeyDir::new()` → 置 `index_rebuilding=true` → `load_keydir_sorted(0)` 重扫新日志 → 换上 key_dir → 清标志。

部分 merge **不能全量重建**——它保留干净段的条目，那些 KeyDir 指针不能动。必须**就地更新**：

1. 不清空 `key_dir`、不置 `index_rebuilding`（干净段条目始终有效，读路径不会断）。
2. 第二趟走 KeyDir 时，遇到指向脏段 file_id 的条目：`read_live` 取值 → append 到新段 → **就地改这条 KeyLoc** 指向新 file_id/pos（`key_dir.insert(key, KeyLoc::Live{file_id: new_id, pos, len})`）。
3. 全部脏段重写完、KeyDir 就地改完 → fsync 新段 → 之后按"崩溃恢复"一节的顺序收尾（删旧 hint → 删旧脏段 → dump 新 hint；顺序不能反过来，理由见那节）。
4. 不需要"重扫新日志"那一步——KeyDir 是在写新段时同步更新的，不是事后重建。

**`index_rebuilding` 标志**：部分 merge 期间不置位（因为 key_dir 始终可用，只是部分条目的指针在更新中）。但要保证：更新某条 KeyLoc 时，新段那行已经 append 了（先写盘、再改指针），否则指针指向未写入的位置。

### 崩溃恢复

每个脏段：写新段 `data.{new_id}.log`（`new_id` 取 `discover_sealed_ids` 与 `active_id` 的 max+1——bitcask **没有** `next_sst_id`，那是 LSM 的词；id 的唯一来源是 `rotate` 的 `active_id += 1`（`bitcask.rs:1434-1475`）和启动时的 discover，部分 merge 的 id 分配要自己写）→ fsync → 更新内存 KeyDir。然后**顺序照现行 merge 的铁律**（`bitcask.rs:1619-1631` 注释）：

1. **先删旧 hint**——此刻旧 hint 里指向脏段的 pos 已经是谎话，留着它，崩了下次 open 会拿它当真索引（现行 merge 为同一理由在重扫前先删 hint）；
2. 再删旧脏段文件；
3. 最后 dump 新 hint。窗口内无 hint ⇒ open 走全量重扫，正确、只是慢。

崩在"新段已写、旧段未删"之间：`full_rebuild`（`bitcask.rs:1311`）按 file_id 升序扫（`discover_sealed_ids` 在 `bitcask.rs:541` 排过序），新段 id 大后扫到，同键覆盖旧段。守卫两个窗口都要：`test_merge_crash_between_write_and_delete_keeps_data` + "删完旧段、没写新 hint"窗口。

### 别漏的簿记

- active（`file_id == active_id`）也是一段，纳入脏段判定；
- 存活率的**分子只有 value len 会高估存活率**（每行还有 key + 头部开销），分母用段文件字节数时分子要补行开销，或阈值按这个偏差校准；
- 新段写完要把它的 Log 挂回 `self.sealed`（现行 merge 是 `sealed.clear()` 后全靠 lazy reopen；部分 merge 保留的干净段句柄不能丢）；
- `index_rebuilding` 全程不置位的前提是"每次就地改 KeyLoc 前，那一行已落新段"——正文已写，落成断言。
- **两趟都要沿用 M40 的分块走查**（`MERGE_CHUNK_KEYS`）：pass 2 若把"指向脏段的条目"一把 `.collect()` 出来再处理，就是 M40 拆掉的那笔 O(库) 内存换个名字回来。
- **多脏段时 hint 循环只走一次**：全部新段写完 → 删 hint 一次 → 删全部旧段 → dump 一次；不是每段一轮。
- **整段全垃圾**（KeyDir 无条目指向它）：直接删文件，不必造新段。

### 两个要写死的决定（二审补）

- **脏的 active 怎么收尾**：active（`data.log`）判脏时，它的存活行重写进新密封段后，active 本身得换成空的新 `data.log`——现行 merge 的 hold_path 换手法（`bitcask.rs:1568-1587`）可以直接搬。或者约定 active 本轮不参与（留到 rotate 之后），二选一，写死再动工。
- **阈值与全干净语义**：`EngineConfig` 冻结（`bitcask_max_file_bytes` 那批就在里面，`engine.rs:174`）⇒ 阈值先落 `const`。全干净时 merge 近 no-op（不写段、不动 hint），bench 的 merge 格读数含义跟着变，手册注一句。

## 第 4 项：`search 末页(免 total)` 新格 + `find_back_n` 新原语

### 靶子改正

bench `search 末页`（`engine.rs` 约 5001 行）用 `SearchQuery::contains("", last_page, page_size)`，`need_total` 默认 true（`types.rs:259` 字段、`contains` 构造器 271 行置 true；初版写 235，那是 `KeyMatchMode`）。20M 档 80.7s 里 total 数全库是主导（`docs/test.txt`：末页带total 80.7s、首页带total 79.8s，而免total 首页仅 40.9ms——差的就是数全库那一遍）。**带 total 的末页改不了**。

`reverse_scan`（`lsm_tree/kv_ops.rs:216`）是 `self.scan(); v.reverse()`——**先全量物化再反转，O(库)**。`reverse_scan(None,None).take(100)` 还是 O(库)，不能用。

### 改法

**新增一格 `search 末页(免 total)`**，走 `find_back_n` 新原语。

**"为什么不能循环 `seek_prev`"这段原稿是错的，撤回**：`seek_prev_with`（`store.rs:615-633`）自己就是那个循环——被拒之后 `bound = raw`（`store.rs:632`），版本键合同"`raw ‖ version_be` > `raw` ⇒ 整组自动排除、更小的键全在"（`store.rs:608-610` 注释原文）让循环不需要任何"减 1"。"N 条"完全可以按这个现成机制循环取。

`find_back_n` 仍然值得做成一个原语，理由降级为工程性的：一次调用收 N 条、把推进与判定封装在一处，bench 和将来调用方不必各自手写循环。

**`find_back_n` 设计**：`find_back`（`lsm_tree.rs:1465`；初版写 1432，那是 `range_scan_at`）有 `excluded: HashSet<Vec<u8>>` 循环——跨源定论成 Drop/不可见的键记进 `excluded` 再找更小的。注意两点：它的 `excluded` 记的是**编码键**；且它只服务"取 1 条"（命中即返回，从不面对"同键旧版本"）。`find_back_n` 就是把它一般化成"收集 N 条**逻辑键**"：

```rust
/// 从库尾取 N 条**逻辑键**（每个 raw_key 一行、取它最新可见的那版），升序返回。
/// low/high 是 raw_key 界；None = 无界（全库 = low=None, high=None）。
///
/// 本质是 [`crate::common::seek_prev_with`] 的一般化："取 1 条"改"收 N 条"。
/// 推进方式同款：下界收到刚找到的 raw_key 本身——它的版本行 `raw ‖ ver` 全都 > raw，
/// 整组自动出局，不会在同一把键的旧版本上打转（`store.rs:608-610` 的合同）。
pub fn find_back_n(
    &self,
    low: Option<&[u8]>,
    high: Option<&[u8]>,
    snap_seq: u64,
    n: usize,
) -> Vec<(Vec<u8>, Option<Vec<u8>>)> {
    let mut out = Vec::new();
    let mut bound: Option<Vec<u8>> = high.map(|h| h.to_vec()); // None = 无上界，不造哨兵
    loop {
        // find_back_opt：find_back 的重构版——界改 Option，None 就不加上界过滤
        // （它现在返回的是**编码键**，调用方要自己 decode）
        let Some((enc, _)) = self.find_back_opt(low, bound.as_deref(), snap_seq, |_, _| true)
        else { break };
        let Some(vk) = crate::common::decode_key(&enc) else { break };
        let raw = vk.raw_key;
        bound = Some(raw.clone()); // 无论活没活，下一轮都严格往更小走
        // 可见性 + TTL 判定复用 seek_prev 的 live 闭包形状（`kv_ops.rs:243-249`）：
        let logical = self.latest_visible_raw(&raw).and_then(|(_, v)| v);
        match crate::common::live_record_of_logical(raw.clone(), logical, now_unix_secs()) {
            Some(rec) => {
                out.push((rec.key, rec.value));
                if out.len() >= n { break; }
            }
            None => {} // 墓碑/过期：不计入 N，继续往前
        }
    }
    out.reverse(); // 收集是降序，末页按 SearchPage 合同升序交出
    out
}
```

⚠️ 初版草图在这里的三个坑，别照抄回去：

1. `find_back` 返回的是**编码键**（版本键）——`seek_prev` 的调用方在 `kv_ops.rs:239-241` 自己 `decode_key` 才拿到 raw。草图直接 `(key, val)` 进 `ExportRecord` ⇒ 用户看到带版本后缀的键。
2. excluded 按**编码键**记拦不住同键旧版本：更新过的键（20M 档 ≈ 200 万把）有多个可见版本，按编码键排除，下一轮最大键就是同一把键的旧版本——末页 100 行里全是重复键 + 旧值。要么按 decode 后的 raw_key 记 excluded，要么像上面那样收紧下界（推荐后者，连 excluded 都省了）。
3. 墓碑/过期判定要复用 `live_record_of_logical`（`store.rs:461`）那套，别只看 `EntryValue::Drop`——TTL 过期在信封里，`find_back` 的跨源定论看不见它。

`find_back_opt(low: Option<&[u8]>, high: Option<&[u8]>, snap_seq, accept)` 是 `find_back` 的重构版：界改 `Option`（None = 无界，不造哨兵——任意字节空间没有"最大值"，初版想造 `b"\xFF"×N` 的念头就是从这里来的，删掉）。

**这条反向路径是 O(块) 不是 O(库)——`docs/test.txt` 五档实测已证**：lsm seek_prev 600k→20M（行数 33×）单价 134.6→162.2 µs（1.2×），剪枝合入后单价基本不随库涨（M78 每块价证据 `CHANGELOG.md:898` 仍有效）。N=100 时 100 × O(块) ≈ ms 级。

### 集成路径（最后一处：怎么从 bench 调到 find_back_n）

bench 用 `Box<dyn KvTxn>`，`search_keys` 是 trait 方法。`find_back_n` 是 LSM 内部方法，`Box<dyn KvTxn>` 摸不到。两条路：

- **(a)** `VersionedStore`（内部 trait）加 `scan_candidates_reverse`，`search_page_walk` 末页分支调它。干净但要改内部 trait + 四引擎各加实现。
- **(b)** `KvTxn`（公开 trait）加 `search_last_page(page_size) -> SearchPage`，默认实现 = `reverse_scan(None, None)` 截尾（O(库) 但**正确**；正向 offset 翻页不知道 total，根本到不了"末页"），LSM 覆盖成 `find_back_n`。**推荐 (b)**——只加一个默认方法，现有调用方不受影响，只有 LSM 覆盖。

```rust

/// 从库尾取 page_size 行（免 total）。默认 = reverse_scan 截尾（O(库) 但正确）；
/// LSM 覆盖成 find_back_n（O(页宽×块)）。
fn search_last_page(&self, page_size: usize) -> SearchPage {
    // ⚠️ 初版默认实现 `SearchQuery::contains(b"", usize::MAX, page_size)` 是错的：
    // skip = usize::MAX ⇒ 一行都进不了窗口还走完全库（空页 + O(库)），三家不覆盖全踩。
    // 正向 offset 翻页在不知道 total 时到不了"末页"，默认只能反向。
    let mut items: Vec<_> = self.reverse_scan(None, None).into_iter().take(page_size).collect();
    items.reverse(); // reverse_scan 降序；SearchPage.items 合同是升序（types.rs:302）
    SearchPage { items, total: None, page: 0, page_size, total_pages: None, has_next: false }
}
```

LSM 的覆盖走 `impl_engine!` 宏开关（落点见"集成路径"末尾那条），示意：
```rust

        .map(|(key, val)| ExportRecord { key, value: val.and_then(|v| /* 剥壳，同其他出口 */) })
```

⚠️ 初版草图的两处：`find_back_n(b"", &[], ...)` 把切片塞给了 `Option<&[u8]>` 签名，`&[]` 当上界 = 空结果；`has_next = items.len() == page_size` 判的是"**前面**还有"（那是 has_prev），`SearchPage::has_next` 的合同是"**后面**还有没有"（`types.rs:313`）——末页语义下恒 `false`。

## 第 6 项：memory 启停持久化 + 四库同步 + bin 归一（用户追加）

### 现状（已核）

- memory 无任何持久化：`impl_engine!` 的 `path: none` + `durable: no`（flush/checkpoint 双 no-op，`engine.rs:1168` "纯内存引擎：无盘可落"）。bench 对 memory 的冷重开是**特判跳格**——`engine.rs:4865` 直接打印"（内存引擎不落盘：重开 = 空库）"不计时，5129 一带的"再冷重开"同。
- 跨库搬运原语已有：`migrate`（`engine.rs:5573`）——游标分页、每页一事务、**TTL 在源侧读**（`get_meta`，注释里记着第一版丢 TTL 被环测抓出来的教训）、**覆盖写**、墓碑过滤；守卫 `migrate_walks_a_ring_of_engines_byte_for_byte`（`engine.rs:2229`）。
- 路径不用动 `EngineConfig`：`StorageConfig.data_dir`（`STORAGE_DATA_DIR`，默认 `./data`）+ `engine_dir()` = `data_dir/<engine>`（`engine.rs:638-667`）。memory 分支"建目录什么都不做"要拆。
- bin：12 个引擎 bin 全是 Cargo.toml 显式 `[[bin]] path` + 前缀名（`Cargo.toml:34-77`）。**层级不统一**：bitcask/bplus/memory 的 export/import 开 **MVCC 层**，唯独 lsm 一对开**裸 `LSMTree`**（KV 层，带 seq）——键/值语义不同层，直接互导有漂移风险。
- 文件格式共享 `common/kv_snapshot`：JSONL + BPEXP001/002（key/value/seq），**没有 TTL 字段**——今天走文件同步必丢 TTL（`migrate` 活着带 TTL，文件格式没有）。

### 设计

**1) memory 持久化（启停各一次 = 优雅停止不丢，不是崩溃安全）**

- 落点：`memory::MVCC` 加快照路径 `Option<PathBuf>`——facade 打开时 = `data_dir/memory/snapshot.bxp`；裸 `MVCC::new()`（bin 直连）= None，不受影响。
- **启停各一次，其余全不碰文件**（用户钉死）：open 时有快照就流式读入重放（`set_raw`/`set_with_ttl`，按页一事务，照抄 migrate 写侧），已过期的行跳过；`MVCC` 的 `Drop` 写一次整库快照（best-effort，失败只 log）。`flush()`/`checkpoint()` **维持 no-op**——`@durable no` 臂整支不动，bench 的 flush 格一个数不变；Drop 写发生在引擎句柄释放时（计时格外），20M 档只是收尾慢一点、格子不失真。
- 这是优雅停止的持久化，**不是崩溃安全**（进程被杀 Drop 不跑）；durable/WAL/merge 语义不变，`engine.rs:49` 等"memory 不能持久化"的 doc 措辞同步改。
- 快照期间的 TTL 行：按台架验收政策的 persist 处理（42ca438 那课），别让"快照耗时内过期"变假红。
- **二选一已定（2026-11-01 用户口径）**：采"只 open + Drop"，`flush() = 写整库快照` 那条**不采纳**。memory 碰文件只有两次——启动读一次、停止写一次；运行期所有 set/delete/事务/flush/checkpoint 一律不碰文件。代价写明：**没有手动存盘口子**，想中途落盘只能释放句柄（或走 export 工具）。
- **这一支独有的两个坑（实现时堵）**：
  ① `std::process::exit` 收尾 = Drop 不跑 = 快照不写。现有 bin 里 35 处 exit（11 个 bin 文件），memory 导入那 4 处（`src/memory/bin/import_kv.rs:54,71,75,113`）全在建库（同文件 `132` 行 `MVCC::new()`）之前 ⇒ **今天不丢**；但统一 import 工具的"校验失败/收尾"分支天然排在导入之后，一写成 exit 就正好落在 Drop 之前把快照吞掉。规矩：先 `drop(db)` 再 exit。守卫：导入 → 释放句柄 → 重开 → 读回行数。
  ② 同一 `data_dir/memory/snapshot.bxp` 上开两个句柄 = **后 Drop 的整份覆盖前一份**，且 open 侧会读到另一句柄写的快照（跨库环测、同库双开都踩）。要么每个实例独立 data_dir，要么钉一条"同一快照路径只允许一个写快照句柄"。

**2) KvRecord v3（BPEXP003：+8 字节 expire_unix_secs，0=永久；读侧三版都认）**

- 001 逐字节兼容不动（`kv_snapshot.rs:749` 有逐字节守卫）；JSONL 加可选 `expire` 字段。memory 快照、统一 export/import 用同一种文件——一份编解码、一份守卫管两头。

**3) 同步语义（"存在的不管，缺失的插入"，钉死成自洽）**

- 载体两个：`sync(from, to)` 顶层新函数（**不是 trait 方法**，合同不破）——migrate 的分页骨架 + 冲突策略；统一 import 工具 = 文件版的同一套判定。
- 冲突策略 skip-existing：目标库"**见过**这把键"就整个不动（值、TTL、墓碑全不碰），没见过才插入。幂等：同一份文件导两次，第二次 0 插入。
- "见过"**含墓碑**：墓碑 = "我知道这把键、它被删了"，不是"没见过"。落实现场先核 `exists()`/`get_meta()` 对墓碑的真实返回（trait 只转发 inner，`engine.rs:965-970`；四家行为要统一验证）——若 `exists()` 把墓碑当不存在就得换口径，否则重复导入会**复活已删键**，恰是不自洽。
- 明确不同步的东西：**删除不传播**（文件/快照里没有墓碑行，skip-existing 也不覆盖墓碑）——这是快照同步不是复制协议；要同步删除走 `migrate`（覆盖语义）或应用层自己管。TTL：已存在键的 TTL 不刷新；新插入按"导出记的 expire − now"起算（与 migrate 同式）。
- 守卫：交集+差集形状（目标已有 k1=旧值，源有 k1=新值 + k2）⇒ sync 后 k1 不动、k2 补齐；复活守卫（目标墓碑 + 源活值 ⇒ 不复活）；四家环测照 migrate 加一套；TTL 跨 sync 保 expire。

**4) bin 归一**

- 根目录 `bin/`：`export_kv.rs` / `import_kv.rs` 两个统一工具，`--engine bitcask|bplus_tree|lsm_tree|memory --dir PATH --format jsonl|bin`，走**门面 `open_engine`**——四家同一条读写路径，lsm 裸层那对退役（`--with-seq` 不进统一工具：seq 只对 lsm 有意义，带着就是给跨库互导埋漂移）。
- 4 个 bench/bench_bulk 平移进 `bin/`，主逻辑不动（全是绝对 crate 路径，没有相对导入要改）；Cargo.toml 只改 path。
- `[[bin]]` 12 条 → 8 条（2 统一 + 4 bench + 旧 lsm 对退役）；根 `bin/` 不在 cargo 自动发现路径里，显式 path 条目保留（本就是现状写法）。
